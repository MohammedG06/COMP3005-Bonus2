# REPORT_M1.md: measurements

The tables below were produced by the scripts in `scripts/`. Machine: Intel Core i7-9750HF, 16 GB RAM, Windows 10, Python 3.14.7. Page and hit counters are deterministic and were identical on Linux (Python 3.14.6).

## 1. Capacity: computed by hand vs measured

`python scripts/m1_capacity.py`

| schema | record bytes L | computed floor(4088/(L+4)) | measured | difference |
|---|---|---|---|---|
| all INT (4 columns) | 16 | 204 | 204 | 0 |
| short VARCHAR(10), 8-char values | 18 | 185 | 185 | 0 |
| VARCHAR(200), 200-char values | 206 | 19 | 19 | 0 |

Hand computation (spec 3.3, `floor(4088 / (L + 4))`, the +4 is the slot):

- all INT, 4 columns: L = 4 x 4 = 16, so floor(4088 / 20) = floor(204.4) = 204
- INT + VARCHAR(10) holding 8 characters + INT: L = 4 + (2 + 8) + 4 = 18, so floor(4088 / 22) = floor(185.8) = 185
- INT + VARCHAR(200) holding 200 characters: L = 4 + (2 + 200) = 206, so floor(4088 / 210) = floor(19.5) = 19

Measured = number of slots on a full data page (page 1) of a loaded table. Computed and measured agree in all
three rows, because every row of these tables has the same length. A gap would appear if row lengths differed:
the formula assumes one L for every record, but variable length rows leave a different amount of leftover space
on each page, and a deleted record keeps its space until compaction.

traces**, generated by `python scripts/make_traces.py --out traces` (seeded, so the same files every time).

- trace1: 5,000 uniform random accesses over 200 pages
- trace2: 5,000 accesses, 80% to a hot set of 50 pages and 20% to 450 others

**Trace 3 at B = 64.** LRU gets 0 hits out of 800 (0.0%). The file has 80 pages and the pool holds 64. After page k is
read, 79 other pages are read before page k is needed again, which is more than the pool can hold, so page k was
evicted after 64 more reads and every re-read is a miss. LRU always throws away the page that will be needed
soonest in a loop (sequential flooding). At B = 256 the whole file fits and the hit rate is 90% (720 of 800: only
the first pass misses).

**CLOCK gets the same 0 hits here.** On a loop bigger than the pool CLOCK also behaves like FIFO, so neither
policy fixes flooding. The real fix is a scan resistant policy (for example LRU-K, one of the listed sources).

**Which would I ship?** On the hot-set trace (trace2) at B = 64 LRU gets
66.1% against 61.9% for CLOCK, and at B = 16 LRU is also ahead (19.8% against 19.4%). On the uniform trace CLOCK is
marginally ahead at B = 16 and 64 (differences of 0.0 and 0.3 points), which is noise. LRU is as good or better on the traces
with a hot set; CLOCK's advantage is cheaper bookkeeping (no list to reorder on every hit). I would ship LRU: it is as good or better on the hot-set traces, and the bookkeeping on every hit is its only cost.

## 3. Scan cost

`python scripts/m1_scan_cost.py`

table T: 102000 tuples on 500 data pages

| B | page reads | hits | misses | evictions | max pinned during scan |
|---|---|---|---|---|---|
| 2 | 501 | 0 | 501 | 499 | 1 |
| 8 | 501 | 0 | 501 | 493 | 1 |
| 64 | 501 | 0 | 501 | 437 | 1 |

Page reads are 501 at every B: 500 data pages plus 1 directory page (page 0, which lists the data pages). Nothing is
cached across the scan because every data page is read once and never asked for again, so a bigger pool cannot
produce hits (hits = 0 in every row). "max pinned during scan" is 1: the scan holds one data page at a time,
as the spec requires (the directory page is unpinned before the data pages are fetched).

## 4. Sources

- **Ramakrishnan and Gehrke, Database Management Systems, ch. 9 (storage and files).** I used its slotted page layout (record slots at the end pointing to records, a free space pointer, a directory of pages for the heap file). This is why a page has a small header plus a 4 byte slot per record, and why the record limit is 4084 and not 4088 (the slot needs its 4 bytes).
- **Pavlo, CMU 15-445 lecture notes on storage and buffer pools** ([course schedule](https://15445.courses.cs.cmu.edu/)). The buffer pool lecture explains pin counts and "sequential flooding". It changed my test plan: I added the repeated scan of an 80 page file (trace 3) specifically to see LRU and CLOCK both get 0 hits when the file is bigger than the pool.
- **O'Neil, O'Neil and Weikum, [The LRU-K Page Replacement Algorithm for Database Disk Buffering, SIGMOD 1993](https://www.csd.uoc.gr/~hy460/pdf/p297-o_neil.pdf).** It explains why plain LRU is fooled by scans (it only looks at the last reference). It did not change the code, since I only implemented LRU and CLOCK as required, but it is why I recommend LRU for a mixed workload only with a warning about scans, and why section 6 explains the flooding case in terms of "how many other pages come before this page is needed again".
- **Hellerstein, Stonebraker and Hamilton, [Architecture of a Database System](https://nowpublishers.com/article/Details/DBS-002).** It changed how I split the code: the buffer pool is the only thing that touches the disk manager, and every higher layer asks the pool for pages. ARCHITECTURE.md follows this layering.
